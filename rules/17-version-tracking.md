# 17. 版本号与可视化版本追踪

## 版本来源

1. 每个项目必须有根 `VERSION`，仅保存一个 `MAJOR.MINOR.PATCH` 版本号，例如 `0.1.0`、`0.1.2`；新项目从 `0.1.0` 开始，已有项目保留自己的版本，不用规范包版本覆盖它。
2. `CHANGELOG.md` 记录版本、日期、主要变更、验证和发布状态；版本对应的 Git SHA 是精确代码身份，不能只凭相同版本字符串认定代码相同。
3. 每次形成新的可交付候选时递增版本：修复一般增加 PATCH，兼容功能增加 MINOR，不兼容版本按项目约定增加 MAJOR；不要求每次保存文件都升级。
4. 每个开发提交仍由 SHA 追踪；开发构建可以显示 `0.1.2-dev+<short-sha>`。已有未提交变化的本地预览标记 dirty，不冒充已发布版本。
5. 测试失败修改后生成新候选版本/SHA，之前的测试结论不自动适用于新候选。已发布版本不得复用或回退覆盖。
6. 公共规范自身版本保存在 `rules/source.json` 的 `version` 并在 `rules/README.md` 显示；目标项目 VERSION 与规范版本独立，更新规则不提升业务版本。规范源项目的 VERSION 与规范版本保持一致。

## release 版本

1. 发布候选在 main 中先准备 VERSION、CHANGELOG 和页面版本，提交说明含版本，如 `release: 0.1.0` 或 `feat: ... (0.1.2)`。
2. 按规则 04、09 测试并记录 `Source-Main-Commit` 和 `Test-Commit`；用户确认具体版本和 main SHA 后，release 才指向该批准提交。
3. 在该 release 提交上创建附注标签 `v0.1.0` 等，正常推送分支与标签；标签是版本标识，不是额外分支。禁止覆盖或移动已经发布的标签。
4. 标签说明记录 Version、Source-Branch: main、Source-Main-Commit、Test-Commit（或不适用）、Validated-By: user、Task-ID。测试脚本不进入 release。
5. release 的实际内容必须匹配获批准 main 候选，不为了记录发布 SHA 在候选内反复补交；发布结果写到 main 后续记录或标签，区分候选 SHA 和记录提交 SHA。
6. 回退已有版本须有对应发布授权，明确旧版本和影响；不伪造更高版本号表示旧代码。

## 页面底部版本

1. 所有可视化页面通过公共底部布局显示当前版本，如 `版本 0.1.2`。已有版权信息保留，桌面和移动端清晰可见，不遮挡内容；无可视化界面的项目在版本命令或交付说明中给出版本即可。
2. 版本从 VERSION 或与其一致的构建元数据自动注入，禁止在每个页面独立手写不关联的版本字符串。前端、后端、构建清单和标签应核对一致。
3. 显示当前实际运行/交付构建的版本，不能请求远程仓库的“最新版本”充当本地版本。多服务不同版本时显示产品版本并在详情中列服务版本，不混淆。
4. 标准构建/打包步骤自动生成版本信息，交付前校验页脚与 VERSION 一致；缓存策略保证新版资源不会沿用旧版版本显示。
5. 本规范的静态 HTML 用 `node scripts/sync-docs-version.mjs` 从 VERSION 同步页脚，直接打开 HTML 也可见；`--check` 只检查不写入。迁移到业务项目时按该项目已有构建链适配，不强制引入 Node。
6. 静态文档无运行时 SHA 注入时显示 VERSION，并通过提交/标签及交付回执区分开发与发布状态，不声称页面版本文字就证明 release 已发布。

## 交付检查

- 核对 VERSION、CHANGELOG、构建版本和页脚，记录候选 SHA。
- 核对 test_main 基线与测试提交，未执行的验证明确说明。
- 核对用户批准对象、release SHA、版本标签和远程推送结果。
- 截图或实际页面检查版本显示；仅找到源文件字符串不能代替显示验证。
