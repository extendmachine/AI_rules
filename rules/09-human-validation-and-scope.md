# 09. 隔离测试与任务完成

## 测试原则

AI 自主选择与改动风险相称的验证方法，能独立完成的检查不得全部退回人工。人工确认保留在 release 发布阶段。
为测试编写的接口、脚本、桩、种子数据和配置必须在 `test_main`，不能污染 `main` 或 `release`。

## 隔离流程

1. 按规则 04 固定待测试 main SHA，再创建或复用 test_main 和独立工作目录；不新建 test_main_日期等分支。
2. 测试修改仅作用于 test_main。main 内可以运行不会写入业务数据的现有只读检查；新增测试代码、临时接口或测试数据必须先切到 test_main 的隔离目录。
3. 测试使用独立端口、项目内临时目录、测试数据库或 schema、虚构数据和测试凭据。不得连接生产数据库、覆盖真实文件或对生产账号执行付费、发送、删除操作。
4. 运行前核对实际数据库目标、路径、端口和外部调用目的地，不能仅凭分支名含 test 判断安全；不直接复制生产凭据、客户数据库或真实日志充当夹具。
5. 使用已有运行时和项目内隔离依赖，不污染系统或其他项目；不要递归复制主项目的 .git、密钥或环境到测试目录。
6. 测试报告包含候选 main SHA、test_main SHA、两者差异、版本、命令和结果。测试代码不得改变被测业务行为来制造通过结果。
7. 失败在 main 修复，生成新候选后重新测试。测试专用代码不得整体合回 main/release。
8. 清理本次临时进程和数据，仅清理已确认属于本次测试的内容；保留可复查的测试代码与不含秘密的测试结果，不为清理新增分支或重写历史。

## 自主判断

1. 在已授权任务内，AI 可自主定位根因、修复接口一致性问题、调整实现并完成隔离验证，无需为每个步骤询问。
2. 确实缺少关键业务选择或涉及授权外破坏性操作时，说明具体选择和影响；不受影响的工作继续。
3. 额外优化只列建议，不借测试扩展需求。跨服务修改按模块划分范围和提交，不要求每服务独立分支。
4. 只读审阅不修改 TODO；修改任务在 main 权威记录中更新验证结果和下一步，测试分支的根记录不是实时权威状态。

## 完成状态

- 实现完成：目标范围代码、说明和版本信息完成。
- 测试通过或未验证：分别记录实际执行结果；没有执行不能填通过。
- 已提交/已推送 main：开发同步完成，不代表 release 发布。
- 待发布确认：候选版本与 SHA 已交付，等待用户确认。
- 已发布 release：批准候选已同步并有对应版本标签。
- 已归档：本次任务范围结束，未发布仍明确标注；不为非发布任务强行创建 release。

纯规范或文档任务可用静态一致性检查验收；编写检查脚本仍放 test_main。不得虚构业务运行、人工测试或生产部署结果。
