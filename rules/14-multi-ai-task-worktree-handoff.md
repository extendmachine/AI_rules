# 14. 多 AI 协调与交接

## 三分支下的单写者

1. 默认分支只允许 main、test_main、release；不得为并行任务创建功能或协调分支。
2. main 日常修改采用单写者：同一时刻由一个主执行 AI 整合、修改和提交；其他 AI 可以并行只读分析，返回建议或补丁文本，不并发写同一工作区。
3. test_main 可由另一执行者在独立工作区测试固定 main 提交；main 继续开发不改变该测试候选。test_main 自身也只有一个写入者。
4. release 同步由主执行者在人工确认后串行处理。只有用户明确授权额外分支时，才可扩展为多开发分支并行。
5. 工具已创建的 Worktree 先核对真实路径、分支/HEAD 和占用，不另建重复工作区；不能通过 detached HEAD 开发多条隐藏业务线绕过分支限制。隔离测试工作区可使用 test_main。
6. 既有多分支项目先登记现状；旧分支和旧协调记录的迁移保留有效任务与授权，不自动删除旧分支或遗失工作。

## 权威记录

1. 日常权威索引是登记的 main 工作区 `AI_TASKS.md`，权威进度是同处的 `TODO.md`；非 Git 项目使用项目根记录。
2. main 的主执行者兼任协调者，记录其工作区绝对位置、执行 AI、任务编号和写入范围。test_main 等副本中的状态文件只是候选快照。
3. 不再要求 `.worktrees/coordination/` 或独立协调分支。存在旧协调记录时，由已有协调者交接到 main；未经核实不能当作无人占用。
4. main 主执行者独占写入权威记录。测试执行者通过宿主提供的消息渠道返回结果，或在 test_main 的任务文件记录供主执行者读取，不直接改写 main 索引。
5. 无可用跨 AI 消息工具时，主执行者读取任务文件并串行整合；无法安全协调时串行执行，不创建第二份权威记录模拟共享状态。
6. 当前执行者中断时先核对工作区与实际任务状态，再交接；不能仅因长时间无消息就夺取仍在工作的写入者权限。确认原执行已结束或用户明确指定接管后更新归属。

## 认领与上下文

1. 修改任务最小登记唯一任务编号、执行 AI、目标、分支、工作区、允许/禁止范围和状态。只读任务无需登记。
2. 开始或接续时只看活动任务和本次相关记录，不要求每次补丁前全文重读。
3. 写入前检查当前文件和占用，保留他人改动；不通过删除他人状态解除冲突。
4. 多服务任务可在同一 main 分支按服务分块处理，记录接口依赖与验证范围，不为目录分层新增分支。

## 交接记录

跨会话接续在 `services/<service>/ai-tasks/<task-id>.md` 保存服务任务；无服务的项目级任务写入根 AI_TASKS。
记录至少包含：目标、执行者、工作区/分支、最近已知 SHA、修改范围、关键决定、已做检查、未完成事项及下一步。
测试记录另包含 Source-Main-Commit、Test-Commit、版本、测试差异及结果；秘密值不写入记录。

任务状态：开发中、实现完成、测试中、测试未通过、待发布确认、已发布 release、已归档。
交接先核对真实文件与 Git 状态，再接手；版本或记录差异能依据事实解决时自主继续，未解决的实际冲突只暂停相关部分。
