# 04. main、test_main、release 三分支管理

## 分支职责

默认只允许以下三个本地及远程分支；允许按需创建，不要求空项目立即建齐：

| 分支 | 用途 | 内容边界 |
| --- | --- | --- |
| `main` | 日常开发、修复、文档与项目协调 | 实际交付代码，不含为测试临时加入的入口、脚本或数据 |
| `test_main` | 从指定 main 提交建立的旁系测试线 | 测试专用代码、隔离配置和虚构测试数据 |
| `release` | 人工确认后的发布线 | 只包含获批准 main 版本及发布来源记录，不接收 test_main 的测试代码 |

不自动创建 `feature/*`、`fix/*`、`service/*`、协调分支或带日期的测试分支。
额外分支必须有用户对名称、用途和范围的明确授权。已有旧分支先登记，不擅自删除、改名、强推或重置。

## 日常开发与自动推送

1. 普通修改直接在 `main`，按任务和服务边界组织提交，不为每个模块另开分支。
2. 确认仓库、分支、工作区状态和单写者归属，保留他人未提交修改；不自动 stash 他人内容来切分支。
3. 完成实现、相关文档和相称检查后，按规则 02 提交。已指定项目远程且有写权限时，可自动创建和推送上述允许的远程分支，无需逐次确认。
4. 先检查远程差异；普通推送被拒绝时先 fetch 并判断，不强推、不覆盖远程更新。不要自动创建远程仓库或改动仓库可见性与保护设置。
5. 推送到 main 是开发同步，不表示已测试、已发布或已部署；使用清晰提交说明和任务编号。
6. 根 `TODO.md` 记录 main 最近已知提交、测试候选、test_main 测试提交和 release 状态。记录不要求包含保存记录本身的 SHA。

## test_main 测试基线

1. 先提交 main 的实际交付内容，取得完整候选 SHA，记录为 `Source-Main-Commit`。从这个提交建立或复用唯一 `test_main`，优先用项目内 `.worktrees/test_main/` 隔离工作目录。
2. 测试专用代码只能写在 test_main；分支隔离不能代替数据库、端口、文件目录和凭据隔离，按规则 09 执行。
3. 复用已有 test_main 时先检查历史、未提交内容和占用；不可为省事直接 reset --hard、强推、删分支或抹掉未保存测试成果。可正常合入目标 main 提交，移除过期测试改动并提交。
4. 明确记录 test_main 相对候选 main 的差异，仅允许测试层改动。若夹带其他业务实现，不能声称测到原 main 版本；需还原为候选业务状态后再测。
5. 测试发现业务问题，回 main 修复并生成新候选 SHA，再更新 test_main 测试；不能只在 test_main 修复后声称 main 已通过。
6. 禁止把 test_main 整体合并、变基或 cherry-pick 到 main/release。需要回收业务修复时只选择已审阅的业务差异，在 main 独立实现和提交。
7. 记录 `Source-Main-Commit`、`Test-Commit`、版本、命令、结果、差异范围和人工确认状态。只读检查不需要为形式新建测试分支；编写或修改测试代码时必须在 test_main。

## 人工确认与 release

1. AI 交付候选版本号、main SHA、test_main 测试 SHA（不适用时写明）、验证结果和剩余风险。
2. 只有用户确认该候选版本完成并允许发布后，才更新 release；“继续开发”、自动测试通过、创建允许分支均不等于发布批准。
3. 发布采用用户批准的精确 main SHA，不盲目合并当时最新 main。main 后续开发不应改变已批准对象；后续提交不能顺带发布。
4. release 不存在时从获批准 SHA 创建；存在时检查其为候选的祖先，可使用正常快进将 release 指向候选。若历史分叉或需要实际内容调整，先诊断并重新验证、确认，不强推。
5. 发布前确认候选已包含正确 VERSION、CHANGELOG、构建版本和页脚；不能在批准后偷偷补入不同内容。
6. 按规则 17 创建对应不可变版本标签，标签说明保留来源和验证记录；release 提交对应版本可用 `release: 0.1.0` 等说明，不能仅依赖分支名判断版本。
7. 发布授权包含该版本 release 分支与标签的正常远程推送，不包含生产部署。不得覆盖同名标签或以重新打标签隐藏代码变化。
8. 发布后在 main 的任务记录中记录 release 与标签 SHA；这类后续记录提交不自动进入已发布版本，也不导致已批准候选失效。
